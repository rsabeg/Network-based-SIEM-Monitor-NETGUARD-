# NETGUARD — Architecture

## 1. Data flow

1. **Sensor** (`sensor/ids_real.cpp`) captures raw packets via Npcap on the chosen network interface.
2. Each packet is checked against 8 detection rules (see below). A match builds a JSON alert and sends it via a raw WinSock2 HTTP POST to the backend (`POST /api/alerts`) — no libcurl/vcpkg dependency.
3. Roughly 1-in-50 normal packets are also sampled and sent to `POST /api/traffic` as a "sensor is alive" heartbeat — separate from alerts entirely.
4. **Backend** (`backend/server.js`) validates, enriches (MITRE ATT&CK id/name, IP geolocation via ip-api.com), and stores each alert in MySQL, then pushes it live to all connected dashboards over Socket.io (`new_alert` event).
5. **Frontend** (`backend/public/index.html`) renders the live feed, recomputes stats/threat scores client-side, and reflects Socket.io events instantly without polling.

## 2. Detection rules (sensor)

| Rule | Type | Trigger |
|---|---|---|
| Port scan | Signature | ≥20 unique destination ports from one source in 10s |
| SYN flood | Signature | ≥30 SYN (no ACK) packets from one source in 5s |
| ICMP flood | Signature | ≥15 ICMP echo requests from one source in 5s |
| Stealth scans (NULL/FIN/XMAS) | Signature | Specific TCP flag combinations |
| Admin port brute force | Signature | ≥5 hits on the same admin port (22/23/3389) from one source in 15s |
| DNS tunneling heuristic | Signature | DNS packet (port 53) over 512 bytes |
| Anomalous packet size | **Anomaly-based** | Packet >5x a source's own learned EMA baseline size (min 20 samples before judging) |
| Blacklisted IP | Signature | Source IP matches a static blacklist |

The anomalous-packet-size rule is the only anomaly-based rule — it learns each source IP's own "normal" over its first 20 packets via an Exponential Moving Average, then only fires on packets dramatically larger than *that specific source's* baseline. This avoids false positives from sources that are simply high-bandwidth by nature.

## 3. Auth & RBAC

- Passwords hashed with **bcrypt**. Self-registration always creates a `viewer` account — admin promotion is a manual, out-of-band DB update.
- `express-session` provides an 8-hour login cookie.
- **Remember Me** is a *separate*, persistent mechanism: a `selector:validator` cookie backed by the `remember_tokens` table. Only the bcrypt hash of the validator is ever stored — a full DB dump can't be used to log in as anyone. Survives an 8-hour session expiring or a backend restart (30-day expiry).
- `requireAuth` middleware gates all dashboard-facing `GET` routes. `requireAdmin` additionally gates the two remediation endpoints (`POST /api/alerts/:id/authorize` and `/dismiss`) — viewers can see recommended actions but can't act on them.

## 4. Simulated Remediation

High-severity alerts get a recommended action string attached at insert time (a plain lookup table keyed by `event_type` — not a "smart" engine). Authorizing an action **only**:
1. Updates `action_status` to `authorized` and stamps `action_authorized_at` in MySQL.
2. Emits `alert_action_updated` over Socket.io.

Nothing is ever sent to `netsh`, `iptables`, or any real firewall/router API. This is deliberately safe to demo live.

## 5. Per-user Clear cursors

Clicking "Clear" on any of the three views (Recent Activity, Live Alerts, Live Traffic Monitor) does **not** delete anything from `alerts` or `traffic_samples` — that data is permanent, shared, and complete for every user. Instead, `user_clears` stores one row per `(user_id, view_name)` with a `cleared_at` timestamp. The frontend hides anything at-or-before that cursor on that view, until something genuinely newer arrives. This makes "Clear" a private, persistent UI preference rather than a destructive action.

## 6. Session Log

A "session" = one continuous run of the Node backend process, from boot to a clean `Ctrl+C` shutdown (`SIGINT`). `GET /api/sessions` computes `total_alerts` / `high_severity_count` **live** for whichever row matches the currently-running `currentSessionId` — scoped deliberately to that exact row (not "any row with `ended_at IS NULL`") so a crashed/never-closed old session can't have its count grow forever from alerts generated by later sessions.

## 7. Database schema (run in order)

1. `netguard_schema.sql` — base `users`, `alerts`, `traffic_samples`
2. `netguard_schema_update_2.sql` — Simulated Remediation columns on `alerts`
3. `netguard_schema_update_3.sql` — `sessions` table (backend run history)
4. `netguard_schema_update_4.sql` — `users` table re-assertion (`IF NOT EXISTS`)
5. `netguard_schema_update_5.sql` — `remember_tokens` table
6. `netguard_schema_update_6.sql` — `user_clears` table
